# システム構成(Architecture)

状態: 再設計(`06_redesign-adr.md`)実装後の構成。

## 1. 全体像

```
ブラウザ(Next.js / React)
   │  supabase-js
   ▼
Supabase
  ├─ Auth        メール+パスワード
  ├─ PostgreSQL  正規化したテーブル + 保存用 SQL 関数 + 集計用ビュー
  └─ RLS         自分の行だけ読み書きできる
```

- Web のみ。スマホもブラウザで使う(レスポンシブ対応済み)。
- 専用のバックエンド API はない。ブラウザが Supabase に直接アクセスする。
- **サーバーが正**。オフライン編集・端末間の同期・ローカル保存はない(オンライン前提)。
- ログイン必須(Supabase の URL / anon key が未設定なら、設定を促す画面を出す)。

## 2. コンポーネントの役割

| 場所 | 役割 |
| --- | --- |
| `app/page.tsx` | メイン画面。4 つのビュー(記録 / 計画 / 種目 / 進捗)を切り替える |
| `components/` | UI 部品。`AuthGate`(ログイン)、`Sidebar`、`WorkoutDetail`、`ExerciseBlock`、`PlansView`、`ExercisesView`、`ExercisePicker`、`ProgressView` |
| `lib/supabase.ts` | Supabase クライアントの生成 |
| `lib/db.ts` | **データベースへのアクセスをここに集約**(取得・保存・削除)。画面は Supabase を直接呼ばない |
| `lib/useData.ts` | 画面用のデータ管理フック。読み込み、編集の即時反映、自動保存、エラー表示 |
| `lib/types.ts` | 画面で使う型 |
| `lib/exercises.ts` | 部位の定義、使用中の種目の判定など |
| `lib/stats.ts`, `lib/utils.ts` | 進捗の集計(再設計予定)、ID・日付のユーティリティ |
| `supabase/migrations/` | DB 定義(`0002` 新スキーマ、`0003` 旧データの移行) |

## 3. データの流れ

### 3.1 起動時
1. `AuthGate` がセッションを確認し、なければログイン画面を表示する。
2. `useData` が、ワークアウト・計画・種目を **1 回だけ**まとめて取得する。

### 3.2 編集(例: セットの重量を入力)
1. 入力は **画面の状態に即時反映**される。
2. 最後の変更から **約 1 秒後**に、そのワークアウト 1 件分(種目・セットを含む)を SQL 関数 `save_workout` に **1 回の通信で**送る。
3. 関数の中で全テーブルをまとめて更新する(トランザクション)。途中で失敗したら全部取り消される。
4. サイドバーに「保存中… → 保存済み」を表示する。失敗したら「保存できていません」と「再試行」ボタン、エラー内容を表示する(画面の入力は消えない)。
5. タブを閉じる・隠す直前にも保存を試みる(ブラウザの仕様で、確実ではない)。

### 3.3 即時に書くもの
- 新規作成(ワークアウト・計画): 作成直後にすぐ保存する。
- 種目マスタの追加・変更・削除: 1 件ずつすぐ書き込む。使用中の種目の削除は DB が拒否する。
- ワークアウト・計画の削除: すぐ書き込む(子データは連鎖して消える)。

## 4. 制限・注意点

事実:
- 2 つのタブ・端末で同じワークアウトを同時に編集すると、**後から保存した側が残る**(同期・競合解決はしない)。
- 入力後 1 秒以内にタブを閉じると、最後の入力が保存されないことがある。
- 通信できない間は保存できない(エラー表示になる)。

推測:
- 個人利用で 1 端末ずつ使うなら、これらは問題になりにくい。
