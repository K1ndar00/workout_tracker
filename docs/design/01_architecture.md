## 1. 全体像

```

│ Web 版 (Next.js)   │     │ モバイル版 (Expo)  │
│ app/ components/   │     │ mobile/            │
│ lib/               │     │                    │
└─────────┬──────────┘     └─────────┬──────────┘
          │  どちらも import         │

        ┌──────────────────────────────┐

        │  types / useAppData / sync   │
        │  stats / utils               │
        └──────────────┬───────────────┘
                       │ supabase-js
                       ▼
```

事実:

- 専用のバックエンド API サーバーはなく、クライアントが `supabase-js` で Supabase に直接アクセスする。
- 端末側にもデータのコピー(ローカルキャッシュ)を持ち、オフラインで使える。

## 3. データの流れ

### 3.1 通常の操作(例: ワークアウトを追加)

1. 画面が `setWorkouts` を呼ぶ → メモリ上のデータ(`dataRef`)を**同期的に**更新して再描画。
2. 変更を検知して、ローカルキャッシュ(`wt:<ユーザー>:data`)に保存。
3. 700ms 後(`PUSH_DELAY_MS`)に `SyncEngine.push` が走り、**前回同期時点との差分だけ**を Supabase に書き込む。
4. 失敗したら状態を `error` にし、10 秒後に再試行する。

### 3.2 他の端末の変更を受け取る

1. Supabase Realtime が `documents` テーブルの変更を通知する。
2. 400ms デバウンス後に `sync()` → `SyncEngine.pull`。
3. サーバーの全ドキュメントを取得し、ローカルと**3 点比較**でマージする。
4. ローカルにしかない変更はサーバーへ書き戻す。

### 3.3 3 点比較(`reconcile`)の考え方

比較対象: ローカル(L)/ サーバー(R)/ 前回合意した状態(S)。

| 状況 | 結果 |
| --- | --- |
| 自分だけにある・未同期 | 新規なので push |
| 自分だけにある・同期済み・未編集 | 他端末で削除されたので、ローカルからも削除 |
| サーバーだけにある・同期済み | 自分が削除したので、サーバーの削除を push |
| サーバーだけにある・未同期 | 他端末の新規なので取り込む |
| 両方にあり、内容が違う・ローカル未編集 | サーバーの編集を取り込む |
| 両方にあり、内容が違う・ローカルも編集済み | **ローカルが勝つ**(後から同期した側が残る) |

## 4. 認証・動作モード

事実:

- Supabase の URL / anon key が**未設定**なら、アカウントなしの**ローカルモード**で動く(状態表示は `local`)。
- 設定済みなら、ログインが必要(`AuthGate`、モバイルは `AuthScreen`)。同期状態は `syncing` / `synced` / `error`。
- データ保護は Supabase の Row Level Security(RLS)で行う。`user_id = auth.uid()` の行だけ読み書きできる。

## 5. 設計上の判断と代替案

事実(コメント・README から確認):

- データを **`documents` テーブル 1 枚 + JSON** で保存している。

推測(学習用のメモ。ADR 候補):

- **選んだ理由(推測)**: Web とモバイルで同じ型をそのまま保存でき、テーブル設計・マイグレーションが少なくて済む。
- **メリット**: 実装が単純。機能追加時に DB 変更が不要。
- **デメリット**: SQL での集計・検索がしにくい。JSON の中身は DB が検証しない。
- **代替案**: 機能ごとにテーブルを分ける(例: `workouts`, `sets` …)。集計が増えたり、データ量が増えた段階で検討する価値がある。

## 6. 確認できた制限・注意点

事実(README・コードより):

- 栄養ログは日付ごとに 1 件(同期のキーが日付のため)。
- 日付は UTC 基準(`toISOString()`)で、日本時間の 0〜9 時台は「前日」扱いになることがある。
- 同じ項目を複数端末で同時にオフライン編集すると、後から同期した側が残る(もう一方の編集は失われる)。
- `pull` は毎回そのユーザーの**全ドキュメント**を取得する(差分取得ではない)。

推測:

- データ量が増えると `pull` が重くなる可能性がある(現状のデータ量では問題になりにくい)。

## 7. 将来検討する可能性がある点

- 日付の扱いをローカルタイムゾーン基準にする。
- 競合時の扱い(項目単位のマージ、更新日時の比較など)。
- 自動テスト(特に `reconcile` は純粋関数なので最初のテスト対象に向いている)。
