## 2. プロジェクトの概要

- **名前**: Workout Tracker(筋トレ記録アプリ)。
- **機能**: ワークアウト記録、トレーニング計画、種目マスタ(部位別)、進捗(部位別・種目別)。
- **構成**: Web のみ(Next.js)。スマホもブラウザで使う。データは Supabase(PostgreSQL)。ログイン必須。
- **保存**: サーバーが正。入力は画面に即時反映され、約1秒後に自動保存(`lib/useData.ts` → `lib/db.ts` → SQL 関数)。オフライン編集・端末間の同期はない。
- **Python**: `analysis/` に、分析スクリプト(アプリ本体とは独立)。
- 詳細: `README.md`、`docs/design/01_architecture.md`、`docs/design/03_database-design.md`。

### 技術
- Next.js 14(App Router)、React 18、TypeScript、Tailwind CSS、`@supabase/supabase-js`。
- Python 3(pandas、matplotlib、requests、pytest)は `analysis/` のみ。

### 第1回の状況
- 開発者は、`docs/learning/00_code-map.md` を読み、ブラウザの開発者ツール(Network)で、`save_workout` の通信を観察した。
- 観察結果: 重量を変えるたびに、通信が1回ずつ(計6回)起きた。
- クラウド側で検証した結果、**待ち合わせは正しく動いており、変更の間隔が1秒より長かったため**と判明。開発者に説明済み。
- 開発者が手を動かして得たこと: 開発者ツールで通信を見る方法、204 の意味(成功、返す値なし)。

### 確認問題(第1回)

| 問 | 状態 |
| --- | --- |
| 1. 重量を3回続けて変えたとき、通信は何回か | 説明済み(間隔が1秒より短ければ1回、長ければ変更ごとに1回) |
| 2. 保存の通信が**失敗**したとき、画面の入力は消えるか。保存すべき変更は、どこに残るか | **未回答。開発者は「わからないかも」と回答。ヒントから始める** |
| 3. `save_workout` の途中でエラーが起きたら、**タイトルの変更**はどうなるか | **未回答。同上** |

**問2・問3 の模範解答**(開発者が考えたあとに、説明に使う。先に答えを言わない)
- **問2**: 画面の入力は、**消えない**(画面の状態は、別に持っているため)。保存すべき変更は、`dirty` という一覧に**戻される**(`lib/useData.ts:83`)。状態は `error` になり、サイドバーに「再試行」ボタンが出る。次の変更や、再試行で、もう一度保存を試みる。
  - ヒントの出し方: 「`catch` の中で、`dirty` に何をしていますか?」「画面のデータは、`dirty` と別の場所ですか?」
- **問3**: **保存されない**(DB は変更前のまま)。`save_workout` は1つのトランザクションなので、途中でエラーが起きると、**全部が取り消される**(タイトルも、種目も、セットも)。画面には新しいタイトルが残っていて、次の保存で、もう一度送られる。
  - ヒントの出し方: 「トランザクションとは何でしたか?」「一部だけ保存された状態は、起きますか?」

### 第1回の残りの課題(任意)
- `lib/useData.ts:8` の `SAVE_DELAY_MS`(1000)を、3000 に変えて、動きがどう変わるか観察する(終わったら 1000 に戻す)。トレードオフ(通信回数 ↔ 保存の遅れ)を、言葉で説明してもらう。
- `console.log` で、`markDirty` と `flush` の呼び出し回数を見る(終わったら、ログを消す。コミットしない)。

### 教え方の方針
- **ボトムアップ**で、小さな単位から。おすすめの読む順番は、`00_code-map.md` の §5。
- 1つの操作(例: 重量を入力 → 保存)を、ファイルをまたいで追う。`ファイル:行番号` を示す。
- 言葉は、初出のときに説明する(イミュータブルな更新、`ref` と `state`、upsert、トランザクションなど)。
- 説明のあとに、**開発者に説明してもらう**(自分の言葉で言えるかが、理解の目安)。
- 間違えても、責めない。事実を確認して、一緒に直す。
